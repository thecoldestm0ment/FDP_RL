## Pilot 장치 구성

`run-blackbox-fdp.sh`의 8 채널, 채널당 8 LUN, 블록당 256 페이지, 페이지당 4096 B, 4 RUH, 1 RG, GC 75/95%를 유지한다. Pilot 설정은 `학습자료/h0_pilot.conf`에 고정했다. `blks_per_pl=64`, `fdp.nru=64`, `devsz_mb=3072`로 맞추고, 나머지 NAND 지연 및 GC 전략은 원래 스크립트 값으로 고정한다. 기본 스크립트의 `blks_per_pl=256`, `devsz_mb=12288` 값을 그대로 둔 채 exposed size만 3072 MiB로 줄이면 물리 용량이 16 GiB로 남아 GC 압력이 달라진다.

계산상 한 RU는 8×8×1×256×4096 = **64 MiB** (16,384 페이지)로 유지된다. 64 RU의 물리 용량은 4 GiB, 노출 용량은 3 GiB다. `bb_check_capacity()`의 기본 reserve는 4 RU이므로 3 GiB 노출은 허용 범위다. guest의 `nvme fdp configs`에서도 `runs=67108864`로 확인했다. FDP의 `lines_per_ru=1`은 `ftl-fdp.c:1705`에 고정되어 있다.

3 GiB namespace에서 A=[0,768 MiB), B=[768,1536 MiB), C=[1536,3072 MiB)로 4 KiB 경계에 나눈다. Rewrite25는 B의 192 MiB = 49,152 페이지를 seed 42로 중복 없이 고른다. Rewrite100은 B의 768 MiB = 196,608 페이지 전부다. 기존 데이터를 보존하는 host read→same-LBA write로 재기록하고 read 양도 별도 기록한다.

## 확인된 FDP 경로와 계측 계획

- `femu.c:280-303`은 namespace PH를 RUH 0,1,2,3에 순서대로 배정한다. `nvme-io.c:1067-1074`에서 PID를 PH/RG로 해석하고, `ftl-fdp.c:1181-1215`에서 `req->fdp_dspec`/`dtype`을 사용해 RUH를 선택한다. guest의 `nvme fdp status`와 실제 write trace에서 PID0→RUH0/RU0, PID1→RUH1/RU1, PID2→RUH2/RU2를 확인했다.
- 기본 `fdp.isolation_mode=0`은 모든 RUH를 PI로 만든다 (`femu.c:143-155`). PI GC는 해당 RUH의 `gc_ru`로 relocation한다 (`ftl-fdp.c:1019-1035`, `:761-846`). B/C 혼합의 피해는 RUH1 victim의 VPC/IPC, 복사 페이지, GC 횟수로 확인한다.
- 기존 vendor log 0xc0은 host pages, GC relocated pages, host-programmed NAND pages를 노출한다 (`nvme.h:1073-1105`, `nvme-admin.c:1498-1537`). 이름 혼동을 막기 위해 요약의 `nand_write_bytes`는 **host-programmed NAND 바이트**, `gc_write_bytes`는 GC 복사 바이트, `total_media_write_bytes`는 두 값의 합으로 정의한다. WAF는 측정 구간 카운터 차분에서 `total_media_write_bytes / host_write_bytes`로 직접 계산한다. `nand_write_pages = host_write_pages`와 `total_media_pages = nand_write_pages + gc_write_pages`를 각 구간에서 검증한다. 이 버전의 log는 누적값이므로 단계 경계마다 원본 512 B를 저장하고 차분한다.
- `FEMU_FDP_DEBUG` 환경변수를 설정하면 `FDP_TRACE`가 활성화된다 (`ftl.c:147`, `ftl.h:604-609`). write trace에 PID, PH, RUH, RG, 현재 RU를 남기도록 `ftl-fdp.c`의 기존 주석 처리된 trace를 활성화했다. `RU_ROTATE`, `GC_START`, `GC_DONE`도 있으며, `GC_DONE`에 victim RU와 복사 페이지가 나온다 (`ftl-fdp.c:1055-1117`). 본 실험에서는 write별 trace의 로그량이 크므로 매핑 확인 때만 켜고, 측정 run에서는 저빈도 snapshot과 GC trace만 사용한다. GC 횟수는 성공한 `GC_DONE` 기록 수와 성공한 `mark_ru_free()` 수를 대응시킨다. trace의 복사 페이지 합은 log 0xc0의 GC 페이지 차분과 일치해야 한다.
- RUH1의 VPC/IPC 분포와 free/victim/full RU 수는 현재 0xc0에 없으므로 별도 저빈도 snapshot 계측이 필요하다. 스냅샷은 동일 FTL thread의 단계 경계에서 수행하고 victim RU의 `ruhid`, `ruidx`, `vpc`, `ipc`, 이동 페이지 수를 기록한다. 상세 계측을 추가할 때 GC 로직 자체는 바꾸지 않는다.

## 준비 환경과 smoke 결과

- FEMU commit: `026eb0ef0ba2f34e4b8711afbb4d35e3f0faf544`, QEMU 10.1.0
- guest: Ubuntu 24.04.5 LTS, Linux `6.8.0-139-generic`, fio `3.36`, nvme-cli `2.8`, libnvme `1.8`
- FDP: 1 RG, 4 PI RUH, 64 RU, RU 크기 64 MiB, 3 GiB namespace
- `io_uring_cmd` + FDP write: PID0/1/2에 각각 4 KiB 1회, fio exit 0
- counter: Host pages 0→3, NAND pages 0→3, GC pages 0→0, WAF 1.0
- RUAMW: PID0/1/2 각각 131072→131064로 8 LBA 감소
- 내부 trace: `PID0→RUH0/RU0`, `PID1→RUH1/RU1`, `PID2→RUH2/RU2`
- 첫 시도에서 `/dev/ng0n1`에 `direct=1`을 주면 fio가 write 전에 거부했다. `io_uring_cmd`는 NVMe passthrough라 filesystem page cache를 거치지 않으며, character device job에서는 `direct` 옵션을 생략한다. 실패 시도 후 0xc0 write counter가 0인 것을 확인했다.
- 원본: `results/h0/preparation/fdp_smoke_trace_JaBmlz/`. 실패 attempt, 성공 fio JSON, 0xc0 전후 binary, FDP status/stats, FEMU 내부 trace를 함께 보존했다.

## 최소 FDP workload generator

`학습자료/fdp_workload.py`는 config를 읽어 phase별 fio job과 `plan.json`을 만든다. 기본은 dry-run이며 실제 write는 config의 `allow_execute=true`, `--execute`, `--confirm-device=/dev/ng0n1` 세 조건이 모두 맞아야 한다.

- 4 KiB random write, seed, A/B/C 범위, 영역별 비율, 영역별 PID, aggregate iodepth와 선택적 IOPS 제한을 지원한다.
- 각 phase의 `host_writes`를 정확한 정수 write 수로 나눈다. phase별 fio 프로세스가 완료된 뒤 다음 phase를 시작하므로 phase/intervention 경계는 host write count로 고정된다.
- `unique_lba=true`인 intervention phase는 fio random map을 사용한다. Rewrite25는 B only 49,152 writes/PID2, Rewrite100은 B only 196,608 writes/PID2로 구성한다.
- Stable/Stale의 shift B PID는 1, Oracle/Soft Redirect/Rewrite의 shift B PID는 2로 설정한다.
- 영역 job은 한 phase 안에서 병렬로 실행되므로 총 영역별 write 수와 PID는 정확하지만, A/B/C 요청의 실제 제출 순서는 guest scheduler에 따라 달라진다. H0 최소 기능에는 충분하며, H1에서 요청 단위의 정확한 전환 순서가 필요하면 단일 큐 generator로 확장한다.
- `학습자료/h0_workload.example.json`의 10,000-write 값은 생성 검증용 template이다. preconditioning 양, 측정 양, aggregate IOPS가 확정되기 전에는 본 실험 config로 사용하지 않는다.

검증에서는 30-write initial과 30-write shift를 실행했다. 두 phase 모두 계획값과 fio 완료값이 일치했고, 0xc0 Host/NAND pages가 3→63, GC pages가 0으로 확인됐다. 합산 iodepth는 각 phase에서 32였다.

## 실행 프로토콜 확정 항목

1. 매 case 새 FEMU 프로세스와 같은 VM 이미지에서 시작한다. guest의 정확한 NVMe namespace 크기, 마운트 여부(`MOUNTPOINT`), FDP 활성화, PID→RUH/RU를 확인한다. OS 디스크와 대상 NVMe를 구분한다.
2. 전체 namespace를 A→PID0, B/C→PID1로 한 번 채운다. 초기 82/6/12 random write를 수행해 GC가 실제로 발생하고 구간 WAF가 안정되는 지점을 pilot에서 찾는다. 이후 **같은 preconditioning host write 양**을 모든 case에 고정하고, phase 경계의 누적 카운터를 저장한다. 빈 SSD의 첫 write 구간은 결과에 넣지 않는다.
3. seed 42로 만든 4 KiB write 요청을 case 간 재사용한다. Stable만 82/6/12를 계속 쓰고 나머지는 38/50/12로 전환한다. 총 배경 write 양, 목표 aggregate write rate, io_uring_cmd, 합산 큐 깊이 32를 고정한다. generator의 plan과 fio JSON에서 영역별 write 수와 합산 depth를 검증한다.
4. Rewrite25/100에서는 shift 시점에 B read→same-LBA PID2 write를 수행한다. intervention 기간의 host/media write, 읽기, IOPS/지연을 별도로 저장한 뒤 모든 shift case에 같은 **배경** host write 양을 실행한다. 전체 비용 표에는 intervention write를 포함하고, post-shift placement 비교에는 배경 구간만 사용한다.
5. 각 phase의 원본 fio JSON/로그, 0xc0 binary snapshot, FDP stats/status/events, FEMU log, 설정/해시, latency percentile, 시계열을 `results/h0/<case>/`에 보존한다. `h0_summary.csv`는 phase와 분모를 명시한 차분값으로 만든다. 실패 run은 별도 attempt로 남기고 완료 run만 요약에 선택한다.

## 본 실험 전 남은 관문

- RUH1 VPC/IPC, free/victim/full RU count의 저빈도 snapshot 계측과 결과 parser를 추가해야 한다.
- Pilot으로 GC가 충분히 발생하고 WAF가 안정되는 preconditioning host write 양을 정해야 한다.
- post-shift 배경 write 양과 aggregate 목표 IOPS를 정하고, 첫 본 실험 전에 모든 case config에 고정해야 한다.
- case별 fresh FEMU 시작, 원본 로그 보존, 0xc0 counter invariant, 완료 attempt 선택을 자동화하는 runner가 필요하다.
