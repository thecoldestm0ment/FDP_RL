# H1 v2 실험 계획 — intervention timing (B turnover 기준)

작성 2026-10-09. H0 v3 본 실험(QD1 9 run) 결과를 바탕으로 H1을 다시 설계했다. 실행 방법은 [H1/v2/README.md](../H1/v2/README.md)에 있다.

수정 2026-10-16 (외부 검토 반영, 실행 전 확정)
- H1-b에 τ 0.3을 처음부터 넣고, 결과를 보고 추가하는 규칙은 없앴다.
- oracle 대조군을 τ 0.6 × seed 3으로 미리 확정했다.
- τ=0 끝점이 H0와 같은지 확인하는 동등성 run을 하나 추가했다.
- H1-a의 "회복 비용"을 "잔여 비용"으로 바꿨다.
- 실행 PC는 H0 v3를 돌린 이 PC다.

## 1. 질문

H0 v3 결과 (4× 시점, Redirect 대비 누적 Media):

| 결과 | 값 |
|---|---|
| Stale 유지 | +18.4 GiB, 1×마다 4.7–5.7 GiB씩 계속 증가 |
| 즉시 Rewrite | +37.2 GiB, 4× 안에 회수 안 됨. 이득은 첫 0.25×에 몰림 |

이를 바탕으로 H1의 두 질문을 정했다.

- **H1-a** — redirect 지연에 따른 누적 Media 비용을 정량화한다. 전환 뒤에도 이전 placement가 남긴 **잔여 GC 비용**이 얼마나 지속되는지 본다.
  - 전환 시점에는 shift 전 old B 중 일부(e^-τ)만 남아 있다.
  - 하지만 지연 동안 새 B 쓰기도 PID1로 갔기 때문에, B의 유효 데이터는 **모두** PID1에 있다(delay smoke trace에서 확인).
  - 전환 뒤 비용은 PID 변경 자체의 비용이 아니라, 이 PID1의 B가 덮어써져 사라질 때까지 생기는 잔여 비용이다.
- **H1-b** — redirect는 즉시 하고, 아직 덮어써지지 않은 old B만 나중에 rewrite하면 즉시 Rewrite보다 나은가? 언젠가 Redirect보다 나아지는 시점이 있는가?
  - 이 비교는 "기다렸다 옮기기(wait-then-migrate)" 전략의 총비용이다.
  - 늦출수록 옮기는 양이 e^-τ로 줄어서, 시점과 양이 함께 바뀐다.
  - 순수한 시점 효과는 oracle 대조군으로 따로 나눈다(5절).

## 2. 독립변수: 개입 시점 τ (B turnover)

τ_B = shift 이후 B에 들어간 application write / B 논리 크기(8 GiB)

- B는 shift 뒤 쓰기의 80%를 받는다. post chunk 하나(0.125× = app 3 GiB)가 τ 0.3이다.
- B 안에서 쓰기가 균등하므로, 덮어써지지 않은 old B는 e^-τ만큼 남는다. 생성기에서 정확히 확인했다(τ 0.6 / 1.2 / 2.4에서 54.9 / 30.1 / 9.1%).
- **수준**

  | 실험 | τ (post chunk) | old B 잔존율 |
  |---|---|---|
  | H1-a | 0.6 (2), 1.2 (4), 2.4 (8) | 55 / 30 / 9% |
  | H1-b | **0.3 (1)**, 0.6 (2), 1.2 (4), 2.4 (8) | 74 / 55 / 30 / 9% |

- H1-b에만 τ 0.3을 넣은 이유
  - H0에서 rewrite 이득이 첫 0.25×(τ 0.6) 안에 몰렸으므로, 그 안쪽을 봐야 한다.
  - H1-a는 stale 비용이 거의 일정한 속도로 쌓이고, τ 0.3까지 쌓이는 비용도 작아서(τ 0.6까지 약 0.4 GiB) 3수준으로 충분하다.
  - 수준은 결과를 보기 전에 고정하며, 사후에 추가하지 않는다.
- 0.5 / 1 / 2를 쓰지 않은 이유
  - chunk마다 seed가 달라서(`SEED + i·7919`), chunk 경계를 바꾸면 app 요청 스트림 자체가 바뀐다.
  - 개입을 chunk 경계에 맞추면 개입 전까지 H0 run과 요청·FTL 상태가 bit 단위로 같다. 그래서 차이는 개입 시점에서만 생긴다.
- 정책 정의
  - **H1-a delay(τ):** post chunk 1..c에서는 B를 PID1(stale)로, c+1부터는 PID2로 쓴다. rewrite는 없다.
  - **H1-b late_rewrite(τ):** shift부터 B를 PID2로 쓴다. chunk c가 끝나면 app 쓰기를 멈추고 rewrite한 뒤, chunk c+1부터 이어 간다.
- **rewrite 대상:** shift 때 있던 old B 중 chunk 1..c에서 덮어써지지 않은 블록만이다. B 전체가 아니다.
  - 생성기가 chunk 1..c의 요청을 그대로 재생해 덮어써진 블록을 빼고, H0 v3 Rewrite와 같은 stride-85 순서로 쓴다.
  - PI에서는 GC가 RUH를 유지한다. 그래서 이 집합은 "개입 시점에 아직 PID1 RUH에 있는 old B"와 같다. 아래 검증 ③에서 FTL로 확인한다.

## 4. 끝점 재사용 (H0 v3 main run)

| 실험 | τ = 0 | never |
|---|---|---|
| H1-a | Redirect | Stale |
| H1-b | Rewrite | Redirect |

- H1 코드(생성기 rewrite 모드, guest, FEMU trace)는 H0 v3와 다르다. 그래서 같은 코드라는 가정 대신 동등성을 직접 보인다.
  - **Stale·Redirect 경로:** run마다 개입 직전까지 FTL state hash와 c0 counter(Media)가 H0 run과 같다(검증 ①).
  - **Rewrite 경로(H1-b τ=0):** 오프라인 LBA 비교만으로는 부족하다. 그래서 동등성 run `equiv_h0.sh`를 돌린다.
    - 구성: H1 코드로 H0 정책 `rewrite`, seed 42, full pre, 전체 B rewrite, post 4 chunk
    - 모든 snapshot의 FTL state hash와 c0 counter가 H0 Rewrite run과 같아야 한다.
    - QD1은 결정적이므로, 상태가 같고 이후 입력이 같으면 끝까지 같다.
    - 오프라인으로도 이미 확인했다: skip 없는 rewrite의 LBA 목록 hash가 seed 3개 모두 H0 Rewrite와 같다.

## 5. 측정 지표

- **주지표:** Redirect 대비 4× 시점 누적 ΔMedia (GiB). Media = NAND user + GC copy.
  - x축은 shift 이후 app 쓰기다. rewrite 쓰기는 x에 넣지 않는다.
  - rewrite의 Media는 실행된 chunk 경계에 더한다.
  - 끝점 하나만 보지 않고 누적 곡선 전체를 보고한다.
- **H1-a 분해**
  - 전환 시점까지의 ΔMedia: 이 구간은 Stale과 bit 단위로 같다.
  - 전환 뒤 **잔여 비용**: 이전 placement로 PID1에 남은 B가 덮어써질 때까지 생기는 ΔMedia. PID1에 남은 B의 감소 곡선(H1_BMAP)을 함께 보고한다.
  - Stale 격차 중 몇 %인지
- **H1-b**
  - rewrite 양(old B의 %)과 rewrite 구간 Media
  - 개입 뒤 Redirect 대비 절약량
  - payback chunk
  - **양 효과와 시점 효과의 분리 (τ 0.6, seed별)**
    ```
    late(τ) − Rewrite(τ=0) = [oracle(τ) − Rewrite(0)]   양 효과: 같은 시점(shift), 적은 양
                           + [late(τ) − oracle(τ)]      시점 효과: 같은 블록·같은 양, 늦게
    ```
- **보고 방식:** 같은 seed끼리의 차이(paired difference)와 seed 3개의 범위를 보고한다. seed 3개만으로 통계적 유의성을 강하게 주장하지 않는다.
- 늦게 개입하면 손해를 회수할 구간이 짧다. 이는 "정해진 기간(4×) 안의 총비용"을 묻는 설계상 의도다.

## 7. 검증 (run마다 자동, 실패하면 캠페인 정지)

1. **개입 전 동등성:** 개입 직전 snapshot까지 모든 snapshot의 FTL state hash와 c0 counter가 H0 baseline과 같다.
   - delay·late_rewrite는 chunk c까지, oracle은 pre 끝까지 비교한다.
   - baseline은 delay가 Stale, late·oracle이 Redirect다.
   - 이것으로 새 코드가 기존 동작을 바꾸지 않았고, 개입 전까지 다른 변수가 없음을 보인다.
2. **요청 스트림:** fill·pre·post 모든 chunk의 LBA hash와 요청 수가 H0 baseline과 같다.
3. **rewrite 대상 = PID1에 남은 old B:** FEMU `H1_BMAP`이 flush마다 모든 B 블록의 owner RUH를 센다.
   - late_rewrite: 개입 직전 PID1 RUH의 B 수 = 생성기가 재생으로 구한 대상 수이고, rewrite 뒤 PID1의 B는 0이다.
   - 이 두 조건이면 두 집합은 같다. rewrite 중 B에 쓰는 것은 대상뿐이고, PI라서 GC로는 PID1 밖으로 나갈 수 없다. 그러니 PID1에 있던 블록은 모두 대상에 들어 있어야 PID1을 떠날 수 있고(PID1 ⊆ 대상), 크기가 같으므로 집합이 같다. LBA 집합 hash는 따로 두지 않는다.
   - oracle: rewrite 뒤 PID1의 B = B − 대상 수이고, chunk c 뒤에는 0이다.
   - 모든 run: shift 때 B 전체가 PID1에 있고, B가 PID0에 있거나 unmapped인 경우가 없다.
4. **τ=0 끝점 동등성:** `equiv_h0.sh`를 1회 실행한다(4절). 캠페인은 이 통과 기록이 있어야 시작된다.
5. **환경 재현:** 본 실험 PC에서 `verify_env.sh`를 돌린다.
   - 짧은 late_rewrite run이 H0 v3를 돌린 PC의 같은 run과 snapshot마다 FTL state hash가 같아야 캠페인이 시작된다.
   - 이것으로 H0 v3 run을 다른 PC의 H1 결과와 비교할 수 있다. H1 코드와 H0 v3의 동등성은 검증 ①이 run마다 따로 확인한다.

## 8. 지금 하지 않는 것

- **QD32:** H1 결과로 비교할 정책(Immediate / best timing / Never)이 정해진 뒤 마지막 validation에서 한다. QD32는 명령 순서 때문에 run마다 결과가 흔들리므로, A/A로 반복 수를 먼저 정한다.
- **workload 변화(H1-2):** 일반화 단계에서 다룬다. τ_B 정의는 쓰기 비율이 바뀌어도 old B 잔존율이라는 의미가 유지된다. 다만 A·C 영역 상태나 GC 압력까지 같지는 않다. B 안에서 쓰기가 고르지 않으면 e^-τ 관계도 깨진다.

- τ 0.6의 음수(−1.4)도 같은 이유로 "Redirect보다 낫다"고 해석하지 않는다. 4× 시점 궤적 차이의 크기는 대략 ±3 GiB다.

### H1-b 양·시점 분해 (τ 0.6, oracle 대조군)

- 늦은 rewrite가 즉시 Rewrite보다 싼 이유는 **옮기는 양이 줄었기 때문뿐**이다.

- 원인

  - 개입 뒤 절약량은 oracle 13.6 GiB, late 4.0 GiB로 크게 다르다.
  - 즉 migration 이득은 shift 직후에 몰려 있어서, 기다리는 동안 그 이득을 잃는다. H0에서 rewrite 이득이 첫 0.25×에 몰렸던 결과와 맞는다.

### 해석과 다음 단계

- 이 workload(B 안에서 균등한 hot overwrite, B가 1×마다 2.4번 갱신됨)에서는 **즉시 redirect + migration 없음**이 가장 좋다.
  - redirect는 늦어져도 손해가 작다.
  - migration은 일찍 할수록 블록당 효율은 좋지만 양이 많다. 늦게 하면 양은 줄지만 블록당 효율이 나빠진다. 그래서 어느 쪽도 Redirect를 넘지 못한다.
- 그렇다면 어떤 workload 변화 조건(자연 overwrite가 느린 경우, 덜 hot한 B 등)에서 migration이 필요해지는가가 H1-2·H2로 이어지는 질문이다.
- 한계
  - QD1 결정적 조건의 결과다. seed 3개의 범위만 보고하고 유의성은 주장하지 않는다.
  - 수준 간 차이 중 약 ±3 GiB 이내는 궤적 차이와 구분하지 않는다.
