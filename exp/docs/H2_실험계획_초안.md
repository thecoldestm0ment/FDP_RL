# H2 실험계획 (초안) — 개입에 비용이 있을 때 host 통계로 시점 정하기

작성 2026-10-17. 상태: **검토용 초안**(run 없음). 근거: [H0 v3 · H1 v2 결과 보고서](H0v3_H1v2_결과보고서_20261017.md)

## 0. 요약

- **H1이 확정한 것.** 빈 RUH가 있으면 "변화를 감지하는 즉시 Redirect하고 migration은 하지 않는다"가 최선이다.
  - Redirect는 데이터를 옮기지 않아 거의 비용이 없고, 늦춰도 손해가 작다.
  - Migration은 어느 시점에도 회수되지 않는다.
  - 그래서 원래 H2 질문("host 통계로 개입 시점을 정할 수 있는가")을 이 조건에서 다시 실험하면 답이 이미 정해져 있다.
- **H2의 제안.** 개입에 실제 비용이 생기는 조건으로 옮겨서 같은 질문을 던진다. 그런 조건은 **쓸 수 있는 RUH가 부족해 PID 대응을 맞바꿔야(swap) 하는 경우**다.
  - 이때 swap은 밀려난 데이터를 hot RUH에 남긴다(cold-in-hot 잔여).
  - 그래서 "지금 바꿀지, 기다릴지, 바꾸지 않을지"가 실제 trade-off가 된다.
- **방법.** 세 단계로 진행한다.
  1. H0/H1 데이터로 비용 모델(stale 손실률, 잔여 비용, 이동 비용)을 만들고 결과를 미리 예측한다.
  2. 예측이 갈리는 시나리오에서 고정 정책을 실행해 검증한다.
  3. host가 관측할 수 있는 통계만 쓰는 규칙이 시나리오마다 최선에 가까운 선택을 하는지 평가한다.
- **규모.**
  - 핵심: 약 37 run(규칙 확인 run 포함), 이 PC에서 약 23시간.
  - QD32 검증: 약 12 run을 따로 한다.
  - 진행은 단계마다 판단 기준을 두고 멈출 수 있게 한다.

## 1. H1에서 H2로: 무엇이 남았나

| H1 결과 | H2에 주는 의미 |
|---|---|
| Redirect를 1×(τ 2.4) 늦춰도 손해는 Stale 비용의 23% 이하다 | 감지가 조금 늦어도 괜찮다. 감지 자체는 어려운 문제가 아니다 |
| 빈 PID2로 redirect한 뒤 잔여 순비용은 0 근처다(±3 GiB) | 빈 RUH가 있으면 오탐(잘못 redirect함)의 비용도 거의 없다 |
| Migration은 옮긴 1 GiB당 Media 5.6–6.9 GiB가 들고, 절감은 1 GiB당 3.1 GiB 이하다 | 4× 구간에서는 어떤 migration도 회수되지 않는다 |
| 같은 블록이면 늦게 옮길수록 손해다(시점 효과 +9.9 GiB) | 옮긴다면 일찍, 살아남을 데이터만 옮겨야 한다 |
| Stale 비용은 cold C가 hot GC에 끌려 반복 복사되는 비용(섞임)이다 | 개입의 가치는 섞임을 얼마나 줄이고, 새로 얼마나 만드는지로 정해진다 |

H1에서 개입이 쉬웠던 이유는 두 가지다.
1. 비어 있는 PID2가 있었다. redirect해도 아무 데이터도 hot RUH에 남지 않았다.
2. 잘못 놓인 old B가 hot이라 금방 덮어써져 사라졌다.

둘 중 하나가 깨지면 결론이 달라질 수 있다. 실제 FDP 장치는 RUH 수가 제한돼 있고(예: 4–8개), 데이터 클래스가 그보다 많으면 RUH를 나눠 써야 한다. 이 경우 hotness가 바뀌면 클래스와 PID 대응을 다시 맞춰야 하는데, 그때 기존 데이터가 엉뚱한 RUH에 남는다.

## 2. 연구 질문과 가설

**H2 질문.** 개입(PID 재대응)에 잔여 비용이 있고 변화가 얼마나 지속될지 모를 때, host가 관측하는 통계만으로 개입 여부와 시점을 정해 시나리오마다 최선의 고정 정책에 가까운 비용을 낼 수 있는가?

- **H2-1 (모델).** 개입의 가치는 다음 식으로 예측할 수 있다.
  ```text
  개입의 가치 = 피한 stale 비용 − 개입이 남기는 잔여 비용 − 일회성 이동 비용
  잔여 비용  = 남겨진 데이터 양 × 섞임 손실률 × 자연히 사라지기까지의 시간
  ```
  이 모델은 H0/H1 데이터로 보정하며, 아래 시나리오의 결과 순서를 미리 맞혀야 한다.
- **H2-2 (결정이 갈린다).** RUH가 부족한 조건에서 최선의 고정 정책은 시나리오에 따라 다르다.
  - 지속적인 변화: 바로 swap
  - 일시적인 변화: 기다리거나 바꾸지 않음
  - 밀려난 데이터가 더는 쓰이지 않음: 바꾸지 않음
- **H2-3 (host 규칙).** host 통계 기반 규칙은 모든 시나리오에서 "최선 대비 손해(regret)"의 최댓값이 어떤 단일 고정 정책보다 작다.
  - host 통계: 영역별 쓰기량, host 자신의 배치 기록, FDP 통계 로그
- 판정에서 약 ±3 GiB(H1의 궤적 차이)보다 작은 차이는 같은 것으로 본다.

### 미리 계산한 예측 (단계 0에서 다듬어 실행 전에 고정)

가정: 밀려난 A(8 GiB)와 hot B가 섞이면 Stale에서 C와 B가 섞일 때와 같은 손실률을 보인다. 값은 Redirect 대비 4× 시점 ΔMedia(GiB)다.

| 시나리오 | 정책 | 예측 |
|---|---|---|
| S1 지속 변화, A 쓰기 10% | 교체 안 함 (= H0 Stale) | +18.4 (실측) |
| | 교체 at chunk 0 / 1 / 2 / 8 | +10.0 / +9.5 / +9.9 / +11.8 |
| | 교체 + 밀려난 A 이동 | 약 +45 (이동 비용이 잔여 비용 약 10보다 훨씬 큼) |
| S1F 밀려난 A가 더는 안 쓰임 | 교체 at chunk 0 | 약 +17–18 (잔여가 줄지 않아 Stale 수준) |
| | 교체 안 함 | S1F의 Stale. C가 20%로 덜 cold해서 이보다 낮을 것으로 추정 |
| S2 0.5× 뒤 원래대로 | 교체 안 함 | 약 +1 (4 chunk 동안의 stale 비용) |
| | 교체 at chunk 1 (+ 복귀 뒤 되돌림) | 잔여가 두 번 생겨 몇 GiB 이상 (단계 0에서 계산) |

예측대로라면 결정은 이렇게 갈린다.
- S1: 바로 교체(약 8 GiB 이득). 1× 이내라면 교체 시점의 차이는 2 GiB 이하로, 구분이 안 된다.
- S1F: 교체 이득이 사라진다.
- S2: 교체하지 않는 쪽이 낫다.
- 모든 시나리오: migration은 회수되지 않는다. 밀려난 데이터가 전혀 안 쓰이는 경우에도 회수에 약 8.7×가 필요하다.

**단계 0의 통과 기준.** 이 모델로 H1 결과를 다시 예측했을 때 ±3 GiB 안에 들어와야 한다. 다시 예측할 대상은 delay의 비용과 migration 순비용(rewrite, late, oracle)이다. 들어오지 않으면 모델을 고친 뒤에 예측을 고정한다.

## 4. 시나리오 설계

### 공통 고정 조건 (H1과 동일)

- 장치: g24, 3 RUH 모두 PI, greedy, lazy 5%, BG 90 / FG 99
- 요청: QD1, latency off, 4 KiB
- 준비: pre 3×, 80/10/10
- 관측: post 4× (32 chunk), seed 42/43/44
- 개입은 chunk 경계에서만 한다.

준비 구간이 H0와 같으므로 shift 직전 FTL 상태도 H0와 bit 단위로 같다. 이건 run마다 확인한다.

### RUH 부족의 재현 방법

- 같은 3-RUH 장치를 쓰되, 정책은 PID0(hot 클래스)과 PID1(cold 클래스)만 쓴다. PID2는 다른 tenant가 쓰고 있다고 가정한다.
- 장치 설정을 바꾸지 않으므로 H0 Stale(교체 안 함)과 H0 Redirect(빈 RUH가 있을 때의 기준)를 그대로 재사용할 수 있다.
- **교체(swap):** shift 뒤 B를 PID0으로, A를 PID1로 보낸다. C는 PID1에 남는다.
  - 이미 쓰인 A는 PID0(이제 hot B가 쓰이는 RUH)에 남는다. 이것이 cold-in-hot 잔여다.
  - 이미 쓰인 B는 PID1에 남는다(hot-in-cold 잔여, H1에서 약 0).

### 시나리오

S1에서 한 가지씩만 바꾼다.

| 이름 | 바꾼 것 | shift 이후 A/B/C 쓰기 비율 |
|---|---|---|
| S0 (H1) | 빈 RUH 있음 | 10/80/10, 지속 |
| **S1** | RUH 부족 | 10/80/10, 지속 (H0와 요청열 동일) |
| **S2** | 변화 지속 기간 | 10/80/10을 0.5×(4 chunk) 동안 쓴 뒤 80/10/10으로 복귀 |
| **S1F** | 밀려난 A의 쓰기 | 0/80/20 (A가 더는 쓰이지 않음, 줄어든 몫은 C가 가져감) |

- **같은 시나리오 안에서의 비교:** 바뀌는 것은 정책뿐이다. 같은 seed는 같은 요청열을 쓰고, 개입 전까지 FTL 상태가 같다. 둘 다 run마다 확인한다.
- **시나리오끼리의 비교:** "어느 정책이 이기는지가 바뀌는가"만 본다. 수치 차이를 특정 workload 변수의 효과로 해석하지 않는다.
- S1F는 A 비율과 C 비율이 함께 바뀐다. hot stream인 B(80%)는 그대로 두어, 밀려난 A가 놓인 RUH0의 환경은 S1과 같게 했다.

## 6. Host 규칙 (단계 3)

**입력.** host가 실제로 알 수 있는 것만 쓴다. FTL 내부 trace(H1_BMAP, H0_STATE)는 검증에만 쓰고 규칙에는 넣지 않는다.

| 입력 | 출처 | 비고 |
|---|---|---|
| 영역별 쓰기량과 비율, turnover | host 자신의 쓰기 카운터 | chunk마다 |
| 영역별로 각 PID에 남은 데이터 양 | host 자신의 배치 기록 | PI에서는 GC가 RUH를 유지하므로 정확함 |
| 장치 WAF | NVMe FDP Statistics 로그(HBMW, MBMW) | 표준. FEMU가 구현함 |
| (선택) RUH별 GC 바이트 | FEMU RUH usage 로그의 hbmw/mbmw | FEMU 확장. 이 경우 표준이 아님을 표시 |

FEMU는 FDP 이벤트 중 Media Reallocated를 지원 목록에만 두고 실제로 생성하지 않는다. 그래서 이 이벤트는 입력으로 쓰지 않는다.

**결정.** chunk 경계마다 다음을 수행한다.
1. 영역의 클래스(hot/cold)가 바뀌었는지 판단한다.
2. 가능한 행동의 남은 구간 비용을 3절의 모델로 예측한다. 행동은 {그대로, 빈 RUH로 redirect, 교체, 교체 + 이동}이다.
3. 지속 기간을 모르므로, 지금까지 쌓인 stale 비용과 교체의 잔여 비용을 비교해 교체 시점을 정한다(ski-rental 방식).
   - 이 비교에는 밀려날 데이터의 양과 turnover를 쓴다. 둘 다 host가 아는 값이다.

예상되는 결정은 다음과 같다.
- S0: chunk 1에 빈 RUH로 redirect
- S1: 이른 교체
- S1F: 교체 안 함(밀려날 A의 turnover가 0이라 잔여가 줄지 않음)
- S2: 교체를 미룸

**평가.**
- 시나리오마다 regret을 구한다. regret = 규칙의 ΔMedia − 그 시나리오에서 가장 좋은 고정 정책의 ΔMedia.
- 규칙의 최대 regret을 각 고정 정책의 최대 regret과 비교한다.
- 이 규칙은 해석 가능한 기준선이다. 이후 RL(H3)의 상태 변수와 보상 설계에도 그대로 쓸 수 있다.

## 7. 검증 (H1과 같은 방식에 추가)

1. **같은 출발 상태:** 모든 run의 shift 직전 FTL state가 H0와 같다(준비 구간이 같음).
2. **개입 전 동등성:** 개입 직전까지 각 시나리오의 "교체 안 함" run과 FTL state·c0가 같다.
   - S1은 H0 Stale과 비교한다.
   - S2는 복귀 전까지 H0 Stale과도 같아야 한다.
3. **같은 요청열:** 시나리오 안의 모든 정책에서 chunk별 LBA hash가 같다.
   - 생성기를 바꾼 뒤에도 기존 패턴의 hash가 H0/H1 run과 같은지 오프라인으로 먼저 확인한다.
4. **잔여 데이터 추적:** FEMU trace를 영역(A/B/C) × RUH 행렬로 넓혀, 밀려난 A가 PID0에서 줄어드는 과정을 확인한다.
   - 이 trace는 읽기만 하므로 FTL 결정에 영향이 없다. 바이너리가 바뀌므로 `verify_env.sh`와 `equiv_h0.sh`를 다시 통과해야 한다.
5. **결정성:** 규칙 확인 run이 같은 결정을 한 고정 정책 run과 hash가 같은지 본다.

| 규칙 | guest 안에서 chunk마다 host 통계를 읽고 다음 chunk의 PID 대응을 결정 |
| 분석 | 시나리오별 기준 run, regret, 규칙 결정의 오프라인 재생 |
| 확인 | 생성기 hash 동등성(오프라인) → 짧은 smoke → `verify_env.sh`·`equiv_h0.sh` 재통과 |

## 9. 단계와 판단 기준

| 단계 | 내용 | 다음으로 가는 조건 |
|---|---|---|
| 0 | 비용 모델 + 예측 고정 (run 없음) | H1 결과를 ±3 GiB 안에서 다시 예측 |
| 1 | S1 (12 run, 약 7.5시간) | 교체 안 함 대비 교체의 이득이 궤적 차이(±3 GiB)보다 큼. 그렇지 않으면 RUH가 부족해도 trade-off가 측정되지 않는 것이므로, 여기서 정리하고 QD32 검증으로 넘어감 |
| 2 | S2 + S1F (18 run, 약 11시간) | 시나리오마다 최선의 고정 정책이 다름. 모두 같으면 고정 규칙으로 충분하다는 결론 |
| 3 | 규칙 구현·확인 (7 run) + regret 분석 | – |
| 4 | QD32 검증 (A/A 먼저) | – |

## 10. 하지 않는 것과 결정이 필요한 것

**이번에 하지 않는 것**
- 빈 RUH가 있는 조건의 감지 실험: H1로 답이 정해졌다.
- 점진적 변화와 영역 안 skew: 일반화 단계로 미룬다.
- 다중 tenant 실제 trace: 이것도 미룬다.

**결정이 필요한 것**
1. H2를 "RUH가 부족해 교체에 잔여 비용이 있는 조건"으로 옮기는 데 동의하는가?
2. 범위: 단계 1(S1, 12 run)만 먼저 돌려 판단 기준을 볼지, 단계 1·2를 한 번에 돌릴지
3. S1F를 넣을지: 규칙이 host 통계로 다른 결정을 내리는지 보는 시나리오다. 빼면 S2만으로 시점 문제를 본다
4. 선택 run(migration 확인 3, 12× 장기 6)을 넣을지
5. seed 수: 3개 유지 또는 5개. 효과가 ±3 GiB 근처면 seed를 늘려도 궤적 차이는 줄지 않는다. 그래서 효과가 큰 조건을 고르는 쪽이 낫다고 본다
